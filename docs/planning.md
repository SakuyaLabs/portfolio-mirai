# 株式会社ミライ工務店 企画・設計ドキュメント（Phase 0〜2 記録）

`sakuyalabs_portfolio_plan.md` の「⑤小規模法人｜コーポレートサイト」案件を、実装前に定義した内容の記録。

## Phase 0｜要件定義・ペルソナ設計

### 架空クライアント
- 株式会社ミライ工務店（従業員15名、地域密着の建築・リフォーム会社）

### エンドユーザーペルソナ（2軸）
- **発注検討者（施主）**：40〜60代。新築・リフォームを検討中で、地元で長く続いている会社かどうかを重視する。
  派手な会社より「堅実そうな会社」を選びたい。
- **採用検討者（協力会社・求職者）**：30〜40代の職人・現場スタッフ。会社の安定感・現場の雰囲気を知りたい。

この2軸を1サイトで満たす必要がある（企画書⑤要件）。

### ゴール（CV地点）
- 施主軸：施工相談・見積り依頼（お問い合わせ）
- 採用軸：採用ページ（⑥Nolanへの導線、簡易情報のみ本サイトに設置）

### 成功指標（KPI）
1. お問い合わせ（施工相談・見積り依頼）到達率
2. 施工事例ページの閲覧数・カテゴリフィルタ利用率

## Phase 1｜情報設計（IA）

### サイト構成（複数ページ。①②③のLP/単一ページ、④の分野別SEOページとも異なる「型」）
| # | ページ | このページの仕事 |
|---|---|---|
| 1 | TOP (`/`) | 事業内容が一目でわかるヒーロー＋実績数字。各ページへの導線を一覧させる |
| 2 | 施工事例 (`/works`) | 新築／リフォーム／リノベのカテゴリフィルタ付き事例一覧。CMS運用を想定したデータ構造で実装 |
| 3 | 会社概要 (`/about`) | 沿革、代表挨拶、企業理念。信頼感の核となるページ |
| 4 | 採用情報 (`/careers`) | 簡易情報のみ。⑥Nolan（採用サイト案件）への導線として最小限に留める |
| 5 | お知らせ (`/news`, `/news/[slug]`) | CMS運用を想定した更新型コンテンツ。一覧＋詳細の2階層 |
| 6 | お問い合わせ (`/contact`) | 施工相談・見積り依頼を完結させる |

### 導線設計
- TOPページに全ページへの入口を用意し、施主・採用検討者どちらのペルソナも迷わず目的のページへ辿り着けるようにする。
- 施工事例（`/works`）はTOPページに抜粋を表示し、「もっと見る」で一覧へ誘導する。
- お知らせ（`/news`）も同様にTOPページへ最新3件を抜粋表示する。

## Phase 2｜デザインシステム定義

- トンマナ：堅実・誠実・奇をてらわない安定感（①〜④のような世界観の強い演出は行わない。これ自体が本案件の技術的な見せ場）
- カラーパレット：
  - Primary（鉄色）: `#3A332C`
  - Secondary（オフホワイト）: `#F5F3EF`
  - Accent（深緑、信頼・地域密着感）: `#4B6B4F`（明背景でのテキスト用途はそのまま使用可、コントラスト比5.39）
    - 暗背景でのテキスト用: `#87AB8C`（iron上でコントラスト比4.87）
  - Neutralは`iron`から派生したグレースケール
- タイポグラフィ：**見出し・本文ともにNoto Sans JP一本**（ウェイトのみ変える）。①〜④で使った装飾的な見出しフォント
  （明朝・丸ゴシック・極太コンデンス・セリフ）はあえて使わない。「唯一のフォントで統一する」こと自体が
  「制作者の作家性を出しすぎない」判断の証明になる（企画書⑤アピールポイント）
- 余白の基準：8pxグリッド／セクション間 96px
- コンポーネント方針：角丸は最小限（4px程度）。装飾的なホバーエフェクト（拡大・彩度変化等）は行わず、
  シンプルな明度変化のみに留める
- アニメーションは①〜④の中で最も控えめ、もしくは使わない。スクロールでのフェードインは行うが、
  ①NAGIの「間」、④はるの「穏やかさ」よりもさらに機能的・実務的なテンポにする（意思決定ログ参照）

## 技術スタック
- Next.js 16 (App Router) / TypeScript / Tailwind CSS v4（CSS-first設定）
- 施工事例・お知らせは、実データはこのプロジェクト内にモックとして保持しつつ、
  **microCMS等の外部CMSへ差し替える前提のスキーマ設計**をコード内コメントで明示する（企画書⑤の技術ポイント）。
  型定義とデータ取得関数を分離し、将来`fetch`ベースのCMS呼び出しに置き換えやすい構造にする。
- 施工事例一覧はクライアント側の状態管理（`useState`）でカテゴリフィルタを実装する
- アニメーション：Framer Motion（使用は最小限、単純なフェードインのみ）
- フォーム：React Hook Form + Zod（お問い合わせフォーム）
- ビジュアル素材：①〜④と同じ方針。写真は使用せず、CSS/SVGの抽象ビジュアル（建材のグリッド・直線的な意匠）で
  世界観を表現する

## ①〜④との差別化ポイント（意思決定ログ）
- **単一フォントファミリーに統一する**：①〜④は案件ごとに世界観を強く演出するフォントペアリングを使ってきたが、
  ⑤はあえてNoto Sans JP一本に統一する。奇をてらわないコーポレートサイトの型を証明するための、
  この案件でもっとも重要な技術的判断。
- **CMS想定のスキーマ設計を明示する**：①〜④はモックデータを直接コンポーネントに埋め込んできたが、
  ⑤では「実データ」と「取得ロジック」を分離し、外部CMS（microCMS等）への差し替えを想定した設計である
  ことをコード内コメントで明示する。
- **複数ページ構成だが、④のような独立SEOページ（`generateStaticParams`によるSSG）ではない**：
  ④は検索意図別の独立SEOページが技術的な核心だったが、⑤の核心は「情報の整理・可読性・更新運用のしやすさ」。
  お知らせ詳細ページ（`/news/[slug]`）のみSSGを使うが、他ページは通常の静的ページとして実装する。

## Phase 5｜品質チェックの記録

### レスポンシブ
Chromeで実施。実測は1568px〜1920px幅のみ（④はる法律事務所のPhase 5と同じく、このセッションでは
`resize_window`ツールが実際には機能しなかったため）。代わりにコード全体をgrepし、複数列グリッドが
すべて`grid-cols-1`ベース＋`sm:`/`lg:`拡張のパターンに従っていること、固定`min-w`要素が存在しないことを
確認した。CLAUDE.mdに④の反省点（`grid-cols-2`を無条件に使うと375px幅で入力欄が圧迫される）を
実装ルールとして明記していたため、今回は実装時点から違反が発生しなかった。

### アクセシビリティ
Lighthouse Accessibility: **100/100**（TOP・施工事例・会社概要・採用情報・お知らせ一覧・
お知らせ詳細・お問い合わせの計7ページで計測）。初回計測で`/works`と`/careers`が98/100
（`heading-order`：h1の直後にh3が来て見出しレベルが飛んでいた）だったため修正した。
原因は、`WorksCard`（施工事例カード）と`PositionsList`（募集職種カード）内の見出しが、
TOPページの抜粋セクション（`h2`の下にネストされる想定でh3固定）と、単独ページ
（`h1`の直後で中間の`h2`がない）の両方から呼ばれる共通コンポーネントだったこと。
`WorksCard`は`headingLevel`propで呼び出し側から見出しレベルを指定できるようにし、
単独ページ（`/works`）専用の`PositionsList`は直接`h2`に変更して解決した。

### パフォーマンス
Lighthouse Performance: **100/100**（`--throttling-method=provided`で計測。TOP: FCP 0.1s / LCP 0.1s、
`/works`（クライアント側フィルタを持つページ）も同様に100、いずれもCLS 0）。
デフォルトのシミュレーションスロットリングは使わず、①〜④のPhase 5で確立した実測ベースの
計測方法（SakuyaLabs External Intelligence `PAT-004`）に最初から従った。

### SEO
Lighthouse SEO: **60/100**（全ページ共通）。唯一の失敗項目は`is-crawlable`で、①〜④と同じく
意図的な設定（`robots: { index: false, follow: false }`）。それ以外（メタ情報、OGP画像の自動生成
`opengraph-image.tsx`、見出し階層、CMS移行を想定したスキーマ設計）はすべて実装済み。
④とは異なり、本案件の技術的な核心はSEO構造化データ（`LegalService`等）ではないため、
JSON-LDは実装していない（docs/planning.md 技術スタックの方針通り）。

### Best Practices
Lighthouse Best Practices: **100/100**（全ページ共通）。
